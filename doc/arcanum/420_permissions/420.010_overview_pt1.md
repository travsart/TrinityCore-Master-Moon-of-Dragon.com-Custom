# Permission Evaluation Pipeline -- Arcanum Wiki

## Overview

The permission evaluation system is Claude Code's multi-layered security gate that decides whether each tool invocation should be allowed, denied, or asked about. It combines static rule matching, mode-based overrides, filesystem path analysis, dangerous pattern detection, an AI-based YOLO classifier (auto mode), and enterprise policy controls. The core principle is "deny wins first" -- deny rules are always checked before any allow rule or mode override.

## How It Works

### Evaluation Order

The main entry point `hasPermissionsToUseTool()` in `src/utils/permissions/permissions.ts` implements a strict pipeline:

```
Step 1 (bypass-immune):
  1a. Deny rule for entire tool?              -> DENY
  1b. Ask rule for entire tool?               -> ASK
  1c. Tool.checkPermissions() (tool-specific) -> tool result
  1d. Tool returned deny?                     -> DENY
  1e. Tool requires user interaction?         -> ASK
  1f. Content-specific ask rule?              -> ASK (bypass-immune)
  1g. Safety check (sensitive paths)?         -> ASK (bypass-immune)

Step 2 (mode-based):
  2a. bypassPermissions mode?                 -> ALLOW
  2b. Entire tool in allow rules?             -> ALLOW

Step 3 (default):
  3. Convert passthrough to ask               -> ASK + suggestions

Post-processing (outer function):
  4. dontAsk mode?                -> convert ASK to DENY
  5. auto mode?                   -> run classifier pipeline
  6. headless/background agent?   -> run hooks, then auto-deny
```

Steps 1f and 1g produce results that are immune to `bypassPermissions` -- safety checks and content-specific ask rules always prompt, even in the most permissive mode.

### Rule Sources

Rules are loaded from 8 sources with increasing priority:

```
policySettings > flagSettings > localSettings > projectSettings > userSettings > cliArg > command > session
```

Enterprise `policySettings` can restrict to managed rules only, effectively ignoring all other sources. Rules are stored in settings JSON under `permissions.allow`, `permissions.deny`, and `permissions.ask` arrays.

### The 4-Way Permission Race

For interactive permission prompts, four async sources race to resolve:
1. **User interaction** (local terminal) -- accept/reject/abort callbacks
2. **Bridge permission** (CCR/claude.ai) -- remote UI decisions
3. **Channel permission** (Telegram, iMessage) -- yes/no via messaging
4. **Hooks + Classifier** (background) -- PermissionRequest hooks and bash classifier

All four use a `createResolveOnce()` guard with an atomic `claim()` method. The first source to claim wins.
